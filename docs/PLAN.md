# wfoxd — план разработки

## Что делаем

Оконное приложение под Windows:

- **слева** — плашки сессий. Сессия = общий набор переменных окружения + текущий
  путь (cwd) + имя/цвет. Всё, что запускается из сессии, стартует с её окружением;
- **справа** — табы, в каждом табе живёт окно любого приложения: терминал,
  drawio, Word, блокнот…;
- изначально табов нет, есть только «+». По нажатию открывается что-то вроде
  старт-меню: список того, что можно запустить в текущей сессии.

Ограничения: Rust, по возможности без сторонних крейтов (Win32 API объявляем
сами), `unsafe` — только в одном тонком слое, остальной код безопасный.

---

## Архитектура

Cargo workspace из трёх крейтов. Граница `unsafe` проходит по границе крейтов,
поэтому её проверяет компилятор, а не код-ревью.

```
wfoxd/
├─ crates/
│  ├─ core/   #![forbid(unsafe_code)]  — модель, логика, парсеры. Без Win32, собирается и тестируется на любой ОС
│  ├─ sys/    unsafe разрешён          — FFI-объявления Win32 + безопасные обёртки. Только Windows
│  └─ app/    #![forbid(unsafe_code)]  — бинарник: склеивает core и sys, UI, обработка событий
└─ docs/
```

### core (безопасный, кроссплатформенный)

- **Модель**: `Session { id, name, env: EnvMap, cwd: PathBuf, tabs: Vec<TabId> }`,
  `Tab { id, title, kind, state }`, `AppState { sessions, active_session, active_tab }`.
- **Команды/редьюсер**: всё, что меняет состояние, — это `Command`
  (`NewSession`, `Launch { profile }`, `CloseTab`, `WindowAppeared { .. }`,
  `ProcessExited { .. }` …), а `fn apply(&mut AppState, Command) -> Vec<Effect>`
  возвращает список побочных эффектов (`Effect::SpawnProcess`, `Effect::ShowWindow`…),
  которые исполняет `app` через `sys`. Так логику можно покрыть юнит-тестами
  без единого окна.
- **EnvMap**: переменные окружения с регистронезависимыми ключами (как в
  Windows), наследование от системного окружения + переопределения сессии,
  сборка блока окружения для `CreateProcessW` (UTF-16, отсортированный,
  `KEY=VALUE\0…\0\0`). Чистая функция, легко тестировать.
- **Раскладка**: расчёт прямоугольников (сайдбар, полоса табов, рабочая область),
  hit-test (по какой плашке/табу/крестику кликнули). Чистые функции от размера
  окна и DPI.
- **Парсер `.lnk`** (формат MS-SHLLINK документирован): из ярлыков Start Menu
  достаём путь к exe, аргументы, рабочую папку, иконку. Самописный — тогда
  не нужен COM `IShellLink`, и ярлык можно запустить через `CreateProcessW`
  с окружением сессии. (`ShellExecuteEx` своё окружение передать не даёт.)
- **Конфиг/состояние**: свой простой формат (INI-подобный) и парсер к нему.
  Профили запуска, сохранённые сессии.
- (позже) **VT-парсер** для собственного терминала, см. этап 9.

### sys (вся небезопасность здесь)

Правила для слоя:

- FFI-объявления пишем руками (`extern "system"` + `#[link(name = "user32")]`
  и т.д.) — только те функции, которые реально используем (ожидаемо 80–150 штук).
  Если станет больно — запасной вариант `windows-sys` (только объявления,
  без рантайма), решение откладываем.
- Наружу не выходит ни одного сырого указателя и ни одной `unsafe fn`:
  - `OwnedHandle` — RAII, `CloseHandle` в `Drop`;
  - `Hwnd` — `Copy`-обёртка над *чужим* окном, которое может умереть в любой
    момент, поэтому все операции над ним возвращают `Result`;
  - `WideStr`/`WideString` — UTF-16 с проверкой на внутренние `\0`;
  - `Process`, `Job`, `WinEventHook`, `Gdi` (DC, кисти, шрифты — всё RAII).
- Каждый `unsafe`-блок с комментарием `// SAFETY:`, линты
  `clippy::undocumented_unsafe_blocks`, `unsafe_op_in_unsafe_fn`.
- Оконная процедура (`extern "system" fn wndproc`) живёт здесь: достаёт
  `Box<dyn Handler>` из `GWLP_USERDATA`, превращает сообщение в типизированное
  `Event` и зовёт обработчик. Паника внутри обработчика ловится `catch_unwind`
  (паника через FFI-границу = UB/abort).
- **Реентерабельность**: `SendMessage`/`SetParent`/`DestroyWindow` и т.п.
  синхронно вызывают нашу же wndproc. Если обработчик держит `&mut self`
  (или `RefCell::borrow_mut`), получим панику. Решение: обработчики не зовут
  Win32 напрямую, а копят `Effect`’ы, которые исполняются после выхода из
  обработчика; вложенные сообщения во время исполнения эффектов кладутся
  в очередь.

### app (безопасный)

Главное окно, отрисовка (GDI, двойная буферизация), обработка мыши/клавиатуры,
исполнение `Effect`’ов, цикл сообщений. Свои контролы рисуем сами (плашки,
табы, «+»); для ввода текста (переименование, редактирование переменных,
поиск в старт-меню) используем стандартный `EDIT` — писать свой текстовый
ввод нет смысла.

## Главный технический риск: встраивание чужих окон

Это то, на чём проект может сломаться, поэтому проверяем первым (этап 1).

### Два способа

**A. Reparent** — `SetParent(чужое, наша_область)`, снять `WS_CAPTION`/`WS_THICKFRAME`,
поставить `WS_CHILD`, `SetWindowPos(.., SWP_FRAMECHANGED)`.

- \+ окно действительно «внутри», двигается и обрезается вместе с нашим;
- − очереди ввода потоков склеиваются: повисший Word вешает и нас;
- − при уничтожении нашего окна Windows уничтожает и дочерние —
  **включая чужие**. Если мы упали, у пользователя закроется несохранённый
  документ. Перед выходом обязательно «отцеплять» всё обратно, а от падения
  это не спасает;
- − проблемы с DPI, меню, фокусом и активацией; у части приложений
  (Office) ломаются всплывающие панели.

**B. Overlay (слежение)** — окно остаётся верхнеуровневым, мы делаем его
owned-окном нашего (`GWLP_HWNDPARENT`), снимаем рамку, держим его точно над
рабочей областью (`SetWindowPos` на наши `WM_MOVE`/`WM_SIZE`, обратная
коррекция по `EVENT_OBJECT_LOCATIONCHANGE`), неактивные табы прячем
`ShowWindow(SW_HIDE)`.

- \+ процессы независимы: зависание или наше падение чужому окну не вредит;
- \+ работает с большим числом приложений;
- − возможны рассинхронизация/мерцание при перетаскивании, нужно аккуратно
  с Z-порядком, сворачиванием, несколькими мониторами.

Предложение: реализовать оба за трейтом `EmbedStrategy`, по умолчанию —
**B**, а **A** включать для конкретных профилей, где он проверен и лучше
(например, conhost). Окончательно решаем по результатам спайка.

### Сопутствующие проблемы (все проверяем в спайке)

- **Найти окно запущенного процесса.** `CreateProcessW` → `WaitForInputIdle`
  → `EnumWindows` по PID работает не всегда:
  - Electron (drawio) порождает дочерние процессы — окно не у того PID.
    Решение: запускать в `Job Object` и искать по всем процессам задания;
  - Word — одноэкземплярный: второй запуск передаёт файл уже работающему
    процессу и завершается. Проверить `winword.exe /x` (новый экземпляр);
  - UWP/WinUI (Windows Terminal, новый Блокнот) — окно принадлежит
    `ApplicationFrameHost`, встраивание, скорее всего, не заработает.
    Помечаем как неподдерживаемые;
  - общий механизм: `SetWinEventHook(EVENT_OBJECT_SHOW)` + окно времени после
    запуска + принадлежность к Job; плюс ручной режим «захватить окно» (выбрать
    из списка открытых или прицелом, как в Spy++).
- **Терминал.** В Windows 11 запуск `cmd.exe` может уйти в Windows Terminal
  (настройка «терминал по умолчанию»), который не встраивается. Проверить
  явный запуск через `conhost.exe`. Долгосрочно — свой терминал на ConPTY (этап 9).
- **Повышенные права.** Окном процесса с правами администратора не управлять,
  если мы без них (UIPI). Помечаем такие окна и не пытаемся.
- **Горячие клавиши.** Когда фокус в чужом окне, наши `WM_KEYDOWN` не приходят.
  Варианты: `RegisterHotKey` на время, пока наше приложение активно, или
  `WH_KEYBOARD_LL`. Выбираем в спайке.
- **Панель задач.** Встроенные окна не должны торчать на панели задач:
  `WS_EX_TOOLWINDOW` (меняет поведение окна) или `ITaskbarList::DeleteTab`
  (COM, вызов через vtable руками в `sys`).
- **Закрытие.** Таб закрывается, когда процесс завершился (ожидание на
  handle процесса через `MsgWaitForMultipleObjects` в цикле сообщений) или
  когда окно уничтожено (`EVENT_OBJECT_DESTROY`). Закрытие таба пользователем —
  это `WM_CLOSE` чужому окну (приложение само спросит «сохранить?»),
  а не убийство процесса.

### Ограничение, о котором надо знать заранее

Окружение сессии применяется **только в момент запуска процесса**. Если
приложение одноэкземплярное (Word, Explorer, многие Electron-приложения
при повторном запуске), новое «окно» откроется в старом процессе со старым
окружением. Для терминалов и обычных программ всё работает как задумано.

## Этапы

### Этап 0. Каркас (≈1–2 дня)
- Workspace из трёх крейтов, `#![forbid(unsafe_code)]` в `core` и `app`.
- Линты: `clippy::pedantic` (выборочно), `undocumented_unsafe_blocks`.
- CI (GitHub Actions): `windows-latest` — build, clippy, test всего;
  `ubuntu-latest` — тесты `core`.
- Манифест (DPI awareness PerMonitorV2, Common Controls v6) встраиваем
  через аргументы линкера MSVC (`/MANIFEST:EMBED /MANIFESTINPUT:…`) из `build.rs`,
  без крейтов.

**Результат:** пустое окно открывается и закрывается, CI зелёный.

### Этап 1. Спайк встраивания (≈1 неделя) — go/no-go
Одноразовый код, можно грязно, но всё равно в `sys`/`app`.
- Окно с одной областью и захардкоженными кнопками запуска:
  conhost+cmd, Блокнот (классический), drawio, Word, Paint, Explorer.
- Обе стратегии A и B, поиск окна через Job + WinEventHook.
- Проверить: ресайз, фокус и ввод, переключение табов, закрытие, DPI на
  двух мониторах, зависание приложения, наше падение (что станет с окнами).
- Записать таблицу «приложение × стратегия × что работает» в
  `docs/embedding.md`.

**Результат:** решение по стратегии по умолчанию и списку поддерживаемых
типов приложений.

### Этап 2. Слой sys (≈1 неделя)
- FFI-объявления, `WideString`, `OwnedHandle`, `Hwnd`, ошибки (`GetLastError`
  → `std::io::Error`).
- Регистрация класса окна, wndproc → `Event`, цикл сообщений с ожиданием
  на handle’ах процессов.
- GDI: DC, двойной буфер, шрифты, прямоугольники, текст, иконки.
- `CreateProcessW` с блоком окружения и cwd, Job Objects, WinEventHook.
- Интеграционные тесты на Windows-раннере (создать окно, запустить процесс,
  дождаться выхода).

### Этап 3. Главное окно и UI (≈1 неделя)
- Раскладка из `core`: сайдбар, полоса табов, рабочая область, «+».
- Отрисовка, hover/pressed состояния, hit-test, DPI-масштабирование,
  светлая/тёмная тема (из реестра, `AppsUseLightTheme`).
- Пока табы — заглушки без окон.

### Этап 4. Сессии (≈1 неделя)
- Создать/переименовать/удалить сессию, переключение плашками.
- Редактор окружения сессии: список переменных, добавить/изменить/удалить,
  cwd (диалог выбора папки — `SHBrowseForFolder` или просто `EDIT`).
- Сборка блока окружения: системное окружение + переопределения сессии;
  поддержка `%VAR%`-подстановки и `PATH` += (префикс/суффикс).
- При переключении сессии показываются её табы, табы других сессий прячутся.

### Этап 5. Табы со встроенными окнами (≈1–2 недели)
- Перенос результата спайка в нормальный код за `EmbedStrategy`.
- Жизненный цикл таба: `Launching` → `Attached` → `Detached`/`Closed`,
  таймаут поиска окна, состояние «не удалось встроить» с кнопкой
  «оставить отдельным окном».
- Заголовок и иконка таба из чужого окна (`GetWindowTextW`,
  `WM_GETICON`), обновление по `EVENT_OBJECT_NAMECHANGE`.
- Закрытие таба, «отцепить» таб (вернуть окну рамку и родителя),
  отцепление всех окон при выходе.
- «Захватить существующее окно» в текущую сессию.

### Этап 6. Старт-меню по «+» (≈1 неделя)
- Всплывающее окно: строка поиска (`EDIT`) + список.
- Источники: профили из конфига (терминал, drawio, Word…), ярлыки из
  `%ProgramData%\Microsoft\Windows\Start Menu\Programs` и
  `%AppData%\Microsoft\Windows\Start Menu\Programs` (свой парсер `.lnk`),
  недавно запускавшиеся.
- Поиск по подстроке/нечёткий, навигация стрелками, Enter — запуск
  в текущей сессии.

### Этап 7. Сохранение состояния (≈3–5 дней)
- Конфиг и состояние в `%AppData%\wfoxd\` (свой формат).
- Сохраняем сессии (имя, окружение, cwd) и список табов как профили запуска;
  при старте — восстановить сессии, табы опционально перезапустить.
- Атомарная запись (временный файл + `MoveFileExW`).

### Этап 8. Удобства (по мере сил)
- Горячие клавиши: новый таб, следующий/предыдущий таб, переключение сессий.
- Перетаскивание табов (порядок, перенос в другую сессию — окружение уже
  запущенного процесса при этом, конечно, не меняется).
- Скрытие встроенных окон с панели задач, свой значок в трее.
- Уведомление/индикатор на табе, если окно мигает (`FlashWindow`).

### Этап 9. Собственный терминал на ConPTY (большой, отдельный)
Встраивание conhost — компромисс. Свой терминал даёт полный контроль,
работает с любыми настройками Windows 11 и позволяет **связать «текущий путь»
сессии с терминалом**: оболочка сообщает cwd через OSC 7 / OSC 9;9, сессия
его подхватывает.
- `CreatePseudoConsole` + пайпы (в `sys`);
- VT-парсер и модель экрана (сетка, атрибуты, скроллбек) — в `core`,
  безопасно и полностью покрывается тестами;
- отрисовка сетки GDI, выделение, копирование/вставка, ресайз.

## Тестирование

- `core`: юнит-тесты (редьюсер, EnvMap, блок окружения, раскладка, парсеры
  конфига и `.lnk`), при желании `cargo miri test` и фаззинг парсеров.
- `sys`: интеграционные тесты на Windows-раннере.
- Ручной чек-лист по `docs/embedding.md` перед каждым релизом: каждое
  поддерживаемое приложение × ресайз/фокус/закрытие/DPI.

## Открытые вопросы

1. «Текущий путь» сессии — это фиксированная настройка, или он должен
   следовать за терминалом (последний `cd`)? Второе реально только со своим
   терминалом (этап 9).
2. Минимальная версия Windows: 10 (1809+, нужен для ConPTY) или только 11?
3. Нужен ли запуск от администратора / встраивание повышенных окон?
4. Что делать при закрытии всего приложения: закрывать встроенные программы
   или отцеплять их в обычные окна?
5. Ручные FFI-объявления vs `windows-sys` — начинаем с ручных, пересматриваем
   после этапа 2.
